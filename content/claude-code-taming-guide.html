Claude Code 调教指南：七种武器，让AI程序员真正听懂你的话

不是AI不够聪明，是你没教会它怎么听话

一场关于「听话」的思考

你有没有这样的经历——

让Claude Code改个bug，它顺手把你整个项目的代码风格都重构了一遍。

你只是想问个问题，它却开始分析你整个代码库的架构。

你在CLAUDE.md里写了「每次提交前跑测试」，它十次里有三次忘了跑。

这不是Claude Code不够聪明。恰恰相反，它太聪明了，聪明到有自己的「想法」。

Anthropic最近发布了一份官方指南，把如何调教Claude Code这件事，讲透了。

核心就一句话：让AI听话，不只需要写好指令，更要把指令放在正确的位置。

先想清楚三个问题

在决定用哪种方式给Claude下指令之前，先问自己三个问题：

  1. 这条指令，在长会话压缩后还需要保留吗？
  2. 我愿意为它付出多少上下文成本？
  3. 这事是必须执行，还是让AI自己判断就行？

想清楚这三件事，七种工具怎么选，心里就有谱了。

七种武器，各有用场

Anthropic把自定义机制分成七类，按「加载时机」「上下文开销」「执行权限」三条线划分。我们来逐一拆解。

第一类：文件级指令（CLAUDE.md）

它是谁：放在项目根目录的Markdown文件，会话一开始就加载，全程常驻。

适合放什么：构建命令、目录布局、monorepo结构、编码规范、团队约定。

优点：任何时候都在，不会丢失。

缺点：每行每句都进入每一次会话，不管用不用得上。

重要提醒：

  • 控制在200行以内
  • 指定一个负责人，像审查代码一样审查它
  • monorepo里给每个团队配子目录的CLAUDE.md，各管各的
  • 个人偏好别往里塞，放自己本地的用户级文件

💡 核心原则：CLAUDE.md是给Claude看的「代码库概览」，不是「操作手册」。

第二类：路径限定规则（rules）

它是谁：放在 .claude/rules/ 目录下，用 paths 字段控制加载时机。

和CLAUDE.md的区别：CLAUDE.md全局常驻，rules可以做精细化路径控制。

举个例子：你有一条规则只适用于 src/api/** 目录，那就加上路径限定。Claude只有在读取这个目录下的文件时才会加载它，其他时候它根本不在上下文中，不占token。

适用场景：跨切面但只在特定代码区域生效的约束，比如「migrations文件只追加不修改」。

第三类：技能（skills）

它是谁：放在 .claude/skills/ 下的文件夹，包含指令、脚本和资源。

加载方式：会话开始时只加载名称和描述，主体内容在调用时才加载。

怎么调用：斜杠命令（如 /code-review）或任务自动匹配。

适合放什么：流程性指令——部署工作流、发布检查清单、代码审查流程。

为什么不用CLAUDE.md：你不想让30行部署流程占用每次会话的token。放进skill，用的时候才加载，省下来的token能让Claude记住更重要的东西。

💡 区分要点：skill在主线程里执行，你能看到每一步，可以随时引导。

第四类：副代理（subagents）

它是谁：放在 .claude/agents/ 下的Markdown文件，定义用于特定副任务的隔离助手。

和skill的核心区别：隔离。

subagent在自己的全新上下文窗口里运行，主会话里只有最终结果回来，中间过程一概不进主上下文。

什么时候用它：做大规模依赖审计，要扫200个包、查每个包的安全公告。如果用主线程，中间结果就能把上下文塞满。换成subagent，每个包派一个代理去查，只把最终汇总报告回来，主线程还能继续推理下一步。

嵌套能力：支持最多五层嵌套，可以编排几十到几百个后台agent。

💡 选择标准：中间结果会塞满主对话且之后不再引用 → 用subagent。希望流程在主线程展开且能随时引导 → 用skill。

第五类：钩子（hooks）

它是谁：在Claude生命周期事件（文件编辑、工具调用、会话开始）触发的确定性控制。

和前面所有方式的本质区别：前面那些都是「给Claude看的指令」，遵循与否取决于模型判断。hooks是代码层确定性触发，模型连选择权都没有。

举例：PreToolUse hook可以检查任何工具调用，返回exit code 2就能直接拒绝它。

适合做什么：

  • 每次编辑后自动跑lint
  • 命令执行前做安全检查
  • 完成后自动发Slack通知

💡 记住：模型选择跑formatter，和formatter自动跑，是两回事。需要「必然发生」的事，就上hooks。

第六类：输出风格（output styles）

它是谁：放在 .claude/output-styles/ 下的文件，把指令注入系统提示。

特点：不会被压缩，指令遵循权重最高。

⚠️ 严重警告：自定义output style会替换掉默认的系统提示——也就是告诉Claude「你是个软件工程助手」的那套指令。包括如何限定改动范围、何时加代码注释、遇到安全顾虑怎么办、完成前先跑测试等等。

后果：Claude能力没变，但角色定位偏了，细节行为会全面偏移。

建议：先用内置的几种——Proactive（自主型）、Explanatory（教学型）、Learning（协作型）。它们覆盖了绝大多数需求，不用自己维护。

如果确实要加：考虑下一种方式。

第七类：追加系统提示（append-system-prompt）

它是谁：在调用时传入的追加指令，只对本次会话生效。

和output style的区别：不做替换，只做加法。不修改Claude的角色，只在默认角色上追加指令。

适合：临时加具体的编码标准、输出格式或领域知识。

注意：塞的指令越多，Claude遵循得越不严格。尤其是互相矛盾的指令放一起，模型往往会各取一部分，结果哪条都没真正落地。

一张表帮你做选择

构建命令、目录布局、编码规范 CLAUDE.md 需要始终记住

五个「踩坑」信号

用着用着发现问题了？对照看看是不是放错位置了：

1. CLAUDE.md里写了「每次X都要做Y」

行为需要可靠发生时，就别依赖模型判断。改成settings.json里的hook。

2. CLAUDE.md里写了「绝对不能做某件事」

指令挡不住所有意外。长会话、压力下、提示注入，都可能让模型翻车。真正的护栏用hooks + permissions。

3. CLAUDE.md里塞了30行流程

流程属于skills。CLAUDE.md只放「始终要记住的事实」。

4. 规则没加paths限定

不加paths，就和塞进CLAUDE.md没区别——永远加载，永远耗token。

5. 个人偏好写进了项目级文件

个人偏好放本地用户级文件，别污染团队配置。

进阶：打包成插件

当你把skills、hooks、output styles组合成熟了，可以打包成一个plugin。

一个团队沉淀出的发布检查skill + 一段PreToolUse阻断hook + 一套专属output style，新成员装上插件就能复用整套工作流，不用一项项配置。

最后

让Claude Code听话，技术只占一半。

另一半是理解：指令放哪里、什么时候加载、给多大权力。

七种机制各有脾气，摆错位置，再精准的指令也会失效。

调教AI和带团队，道理是相通的——把正确的事，交给正确的人，在正确的时间，用正确的方式。
