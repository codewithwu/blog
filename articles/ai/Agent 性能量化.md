
# Agent 性能量化

#### 核心观点
量化 Agent 的性能，不能只看任务是否成功。因为 Agent 涉及多轮交互、工具调用和环境反馈，需要从**结果、过程、系统**三个维度，结合**自动化评测方法**和**工程落地的坑**来全面评估。

---

### 一、三维评估指标体系

| 维度 | 关注点 | 核心指标 | 通俗解释 |
| :--- | :--- | :--- | :--- |
| **结果层** | 任务最终是否达成 | - **任务成功率**<br>- **状态匹配** | 任务完成了吗？系统状态（如数据库）是否正确改变？ |
| **过程层** | 任务完成的轨迹质量 | - **工具调用准确率**<br>- **轨迹效率**<br>- **自我纠错率** | API 选对/参数传对了吗？有没有走弯路？遇到错误能自己修正重试吗？ |
| **系统层** | 工程与成本考量 | - **端到端延迟**<br>- **Token 消耗量** | 响应快不快？运行成本高不高？ |

> **示例**：Agent A 用 3 步订好机票，Agent B 用了 50 步并调用了大量无用 API 才勉强成功。两者性能差异巨大，仅看“结果层”无法区分。

---

### 二、自动化评测方法

不能只靠人工观察，需要自动化手段。

| 评测方法 | 原理与适用场景 | 特点 |
| :--- | :--- | :--- |
| **代码断言** | 对 Agent 生成的代码直接运行单元测试，判断对错。适用于逻辑确定的任务。 | 最客观，结果明确（通过/不通过）。 |
| **状态机比对** | 比对 Agent 操作前后环境（数据库、沙盒文件等）的状态变化。常用于 RPA 或数据库 Agent。 | 真实还原 Agent 对外部世界的影响。 |
| **模型裁判** | 用一个更强大的模型（LLM Judge）作为裁判，根据预设准则（如逻辑、语气、安全性）对 Agent 的输出（如邮件）进行主观打分。 | 解决了没有标准答案任务的评估难题。 |

---

### 三、评测落地的三大挑战与对策

在实际工程中评测 Agent，会遇到以下三个核心挑战：

| 挑战 | 问题描述 | 解决对策 |
| :--- | :--- | :--- |
| **1. 级联错误** | Agent 的步骤是连贯的，第一步规划错，后面全错。难以判断是“规划层”能力差，还是“执行层”（API）质量差。 | **模块化拆解评估**：通过 Mock 技术固定环境反馈，单独对规划层进行压力测试，实现精准归因。 |
| **2. 非确定性** | 大模型每次生成结果可能不同，网络延迟等环境因素也会导致性能波动。 | **沙盒与快照**：使用 Docker 等容器技术，在每次测试前还原环境快照，确保 Agent 每次都在完全相同的起跑线上。 |
| **3. 裁判幻觉** | 模型裁判可能被 Agent 欺骗（如 Agent 假装完成任务），或者裁判自身评估出错，给错误轨迹打出高分。 | **多路裁判机制**：让多个模型共同评估并辩论，交叉验证结果，同时配合人工定期抽检来校准。 |

---

### 笔记总结

量化 Agent 性能是一个系统性工程，应遵循以下路径：

1.  **建立立体指标体系**：从 **结果**（任务成败）、**过程**（轨迹效率）、**系统**（成本延迟）三个层面衡量。
2.  **采用自动化评测**：结合**代码断言**、**状态比对**和**模型裁判**，覆盖确定性与非确定性任务。
3.  **解决工程落地难题**：通过**模块化测试**、**沙盒环境**和**多路裁判**等手段，应对级联错误、非确定性及裁判幻觉等挑战。
